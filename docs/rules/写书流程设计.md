# “三万字一批”写书流程设计

## 结论

这个流程最适合做成一个**有持久化状态的编排型技能**，而不是把 `expand` 改成“一次写三万字”，也不是一个只生成大纲的提示词。

建议名称：`writebook`（分批写书 / 批量写作）

入口：

- 直接调用：`/webnovel:writebook`
- 自然语言：`按三万字一批继续写这本书`、`开始下一批三万字`
- `start` 入口增加“分批写完整本书”路径

它负责调度现有能力：

```text
memory 读档
  ↓
writebook 写前提问与批次规划
  ↓
outline 生成本批章纲
  ↓
expand 按章生成正文
  ↓
continuity 连贯性检查
  ↓
review / aidetect（可选质检）
  ↓
memory 回写剧情、人物、世界、伏笔、进度
  ↓
writebook 生成下一批待填写问题
```

## 为什么必须是“编排型技能”

三万字不是一个单章，而是一个可独立验收的**写作批次**。如果只交给 `expand`，容易出现：

1. 前后章节没有明确的目标、阻碍、结果和代价；
2. 生成中途无法恢复，三万字完成后没有结构化状态；
3. 下一批只能重新把正文全部喂给模型，容易忘记设定；
4. 人物状态、世界状态和伏笔没有自动进入单一事实来源；
5. “完结”没有明确判定条件。

因此需要一个状态机和一组批次档案。

## 用户交互：两阶段，不把提问和写作混在同一轮

### 阶段 A：写前提问

每批开始先读档案，再展示“本批写作确认单”，只提当前批次真正缺失的信息。用户填写完后，流程停在 `待写作`，不提前生成正文。

固定确认项：

- 本批目标：推进哪条主线、哪一卷、从哪一章到哪一章；
- 本批目标字数：默认约 30,000 字，允许末批不足或用户调整；
- 本批必须发生的剧情节点；
- 本批不能发生的内容/雷区；
- 本批情绪与节奏：爽、虐、悬疑、日常、感情等比例；
- 重点人物及其当前目标、关系变化；
- 必须埋下或回收的伏笔；
- 新设定、道具、地点、敌人是否允许加入；
- 视角、人称、文风是否沿用档案；
- 本批结尾希望落在哪种钩子；
- 是否开启连贯性检查、AI 味检测、敏感词校对；
- 用户可追加的自由要求。

如果档案中已经有明确答案，就显示为“沿用档案”，不重复逼问。只对缺口提问。

### 阶段 B：批次写作与提交

用户提交答案后：

1. 锁定本批写作契约，避免写到中途漂移；
2. 生成本批章纲，通常拆成 10–15 章，每章约 2,000–3,000 字；
3. 按章写正文，章尾接钩，正文写入 `正文/`；
4. 达到约 30,000 字后停止扩写，不为了凑字数灌水；
5. 做批次级连贯性检查；
6. 自动生成本批总结和下一批输入包；
7. 更新全书档案；
8. 如果未完结，状态改为 `待下一批提问`，展示下一批问题；如果完结，状态改为 `已完结`。

## 推荐档案结构

在现有书目录上增加：

```text
《书名》/
├── 00_设定.md
├── 01_人物.md
├── 02_大纲.md
├── 03_伏笔追踪.md
├── 04_灵感本.md
├── 05_进度.md
├── 06_投稿记录.md
├── 07_时间线.md
├── 08_写书状态.md          # 当前批次状态机与下一步动作
├── 09_批次索引.md          # 每批的范围、字数、状态、总结文件
├── 批次/
│   ├── 第001批_提问.md
│   ├── 第001批_写作契约.md
│   ├── 第001批_章纲.md
│   ├── 第001批_总结.md
│   ├── 第001批_下一批输入.md
│   └── …
└── 正文/
    ├── 第001章.md
    └── …
```

### `08_写书状态.md` 是恢复点

至少记录：

```text
# 写书状态
- 状态：待下一批提问 / 待用户填写 / 写作中 / 待质检 / 待回写 / 已完结
- 当前批次：第 3 批
- 已完成批次：2
- 当前章节：第 27 章
- 累计字数：约 8.1 万字
- 本批目标字数：约 3 万字
- 本批正文：批次/第003批_正文.md（或正文目录下对应章节）
- 下一动作：回答第 4 批提问
- 最后一次完整回写：2026-06-05
```

### 批次总结必须分层

`第NNN批_总结.md` 不只是剧情梗概，而是下一次写作可以直接使用的“压缩上下文”：

1. **本批剧情摘要**：按章列出发生了什么；
2. **状态变化**：人物目标、关系、伤势、能力、资源；
3. **世界变化**：时间、地点、势力、规则、社会局势；
4. **伏笔变化**：新增、推进、已回收、待回收；
5. **当前悬念**：上一批留下的钩子及读者知道的信息；
6. **未解决冲突**：下一批必须接住的矛盾；
7. **下一批目标**：主线目标、阶段性结果、结尾钩；
8. **一致性警报**：本批发现但暂未修复的问题。

## 状态机

```text
未建档
  → 待读档
  → 待提问
  → 待用户填写
  → 已确认/待规划
  → 待写作
  → 写作中
  → 待质检
  → 待回写
  → 待下一批提问
  ↘ 已完结
```

异常恢复规则：

- `写作中`：读取批次章纲和已写章节，从下一章继续，不覆盖已有正文；
- `待质检`：只做检查，不重复生成；
- `待回写`：先回写档案，再允许开始下一批；
- `待下一批提问`：先展示上一批压缩总结，再提问；
- 用户要求重写：创建修订版，不覆盖已定稿批次，或明确选择覆盖。

## 30,000 字的实际拆分

“三万字”是批次目标，不强行要求模型在一条消息里吐出三万字。默认：

- 10–15 章；
- 单章约 2,000–3,000 字；
- 每 3–5 章做一次小检查；
- 批次结束做一次总检查；
- 最后一批允许低于 30,000 字，以完结为准。

这样既保留用户的批次节奏，又符合章节发布和断点恢复习惯。

## 完结判定

只有同时满足以下条件才标记 `已完结`：

- 主线核心矛盾已解决；
- 主角核心成长弧完成；
- 主要人物结局已交代或有意留白；
- 主线伏笔全部回收，支线伏笔明确标记为留白；
- 最后一批正文有终章收束，不只是一个章尾悬念；
- `05_进度.md`、`03_伏笔追踪.md`、`07_时间线.md`、`08_写书状态.md` 已回写。

## 与现有流程的边界

- `outline`：负责全书/分卷/本批章纲，不负责持续状态；
- `expand`：负责单章正文，不负责三万字批次生命周期；
- `memory`：负责持久化档案，是唯一事实来源；
- `continuity`：负责逻辑核对，不代替总结；
- `review`、`aidetect`：作为可选质检，不阻塞普通写作；
- `writebook`：只负责把这些能力串成“提问 → 写作 → 总结 → 下一批”的循环。

## 推荐的实现形式

第一阶段用 Markdown 技能即可落地：

- 新增 `writebook/SKILL.md`：定义路由、问题模板、状态机、生成与回写规则；
- 扩充 `start/SKILL.md`：增加入口和自然语言触发说明；
- 扩充 `memory/SKILL.md` 与 `project-memory.md`：加入批次状态、批次索引、总结格式；
- 不修改 `expand` 的单章职责。

以后如果 GUI 需要可视化，再把 `08_写书状态.md` 映射成批次面板；不要一开始把流程硬编码进前端，否则会失去跨会话和跨模型能力。
