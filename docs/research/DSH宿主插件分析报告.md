**一句话结论**：`dsh-novel-writing` 是**工程参考价值最高**的（它把"宿主兼容"当成一门工程学科来做）；`oh-story-dsh` 是**写作方法论最厚**的（51.7 MB 里大半是知识库）；`dsh-novel` 是**结构化建模最干净**的（1.4 MB 讲清了一套网文实体模型），但它的依赖策略是**反面教材**。

## 2. 三者的共同点：bundle patch 都只有一行

三个插件的 `cordis.patch.yml` 全都短得离谱：

```yaml
# dsh-novel-writing（12 行，大半是注释）
- insert:
    - id: novel-writing
      name: dsh-novel-writing

# dsh-novel（51 字节）
- insert:
    - id: novel
      name: dsh-novel

# oh-story-dsh（packages/dsh-plugin/cordis.patch.yml，6 行）
- insert:
    - id: oh-story
      name: '@oh-story/dsh'
```

**这不是偷懒，而是一种明确的设计**：patch 只负责**把插件挂进 composition**，其余一切（服务、工具、HTTP 路由、客户端视图、预设同步）都由插件入口在运行时程序化注册。好处有三：

1. **升级不必改配置**——新功能写进 `index.js`，用户更新包即可，不动 `cordis.patch.yml`；
2. **可降级**——宿主缺哪块能力，插件在 `apply()` 里自己判断并少注册一块，而不是配置报错；
3. **安装脚本可幂等**——写一行 patch 比写一段结构化配置好校验（`dsh-novel-writing` 的 `install.ps1` 就是这么做的：往 `cordis.patch.yml` 插一行，且有"固定标记行"防止重复插入）。

**可复用结论**：**如果你要写 DSH 插件，patch 里只放一行 insert，逻辑全放入口。**

# 第二篇｜宿主插件工程机制

> 这一篇是本次分析最有价值的部分。所有结论都有源码依据。

## 3. DSH 插件的入口契约

【实测】`dsh-novel-writing\lib\index.js` 是标准的 cordis 插件模块，导出四样东西：

```js
export const name = 'dsh-novel-writing'        // 插件名，必须与 patch 行的 name 一致
export const inject = [...hostInject]           // 声明的服务依赖（此处 = ['settings']）
const Config = z.object({ ... })                // schemastery/zod 配置模型
export function apply(ctx) { ...; return service }  // 挂载入口，返回服务实例
```

**要点**：

- **`inject` 是"硬依赖声明"**：只声明**必须**存在的服务；`webServer`、`timer` 这类可选能力**不放进 inject**，而是在 `apply` 里探测（`getWebServer(ctx)` 返回 `undefined` 就走降级分支）。【实测 `index.js:37,1461-1466`】
- **`Config` 用 `z.object({...}).default(...)` 定义每一项**，包含 `enabled`、`workspaceRoot`、轮询周期等。配置命名空间必须匹配 `dsh-settings` 的 `/^[a-z][a-z0-9-]*$/`。【实测 `index.js:39-45`】
- **`apply()` 末尾 `return service`**，把服务实例交给宿主——宿主据此把服务注册进 `ctx`，其他插件/工具就能拿到它。
- **服务基类 `Service` 从边界层导入**（`import { Service, z, ... } from './host-boundary.js'`），不是直接从宿主包导入。

### 3.1 完整的扩展面（五条通道，逐个实测）

【实测，详见 `dsh-novel-writing-analysis.md` §A1—A2】一个 DSH 插件能挂五样东西，这是完整清单：

| 通道 | 注册方式 | 实测细节 |
|---|---|---|
| **服务** | `class X extends Service` + `super(ctx, 'novel-writing')` | 服务名是单一事实源（`SERVICE_NAME`），其他插件用 `ctx.get('novel-writing')` 取 |
| **设置节** | `registerSettings(ctx, ns, Config)` | 命名空间 `'novel-writing'`；Config 字段：`enabled` / `workspaceRoot` / `pollMs` / `apiPublic` / `presetAutoSync` / `platforms`(z.dict) / `bindings`(z.dict) |
| **工具** | `defineTool`（**独立工具行**，不在主 patch 里） | 11 个：`novel_list`/`novel_status`/`novel_state_update`/`novel_chapter_read`/`novel_chapter_write`/`novel_gate_check`/`novel_review_submit`/`novel_data_ingest`/`novel_publish`/`novel_requests`/`novel_request_done`。**`output.schema` 一律 `additionalProperties:false`** |
| **HTTP 路由** | `webServer.register({kind:'exact'})` | 13 条 `/novel-writing/api/*`（overview/novel/chapter/gate/request/novel-create/novel-delete/file/request-done/publish/data/preset-sync/compat） |
| **客户端 bundle** | `window.__ModuleLoader__.load({id, factory})` + `ctx.slots.inject/register` | 6 处槽位：`settings.section`(20) / `sidebar.footer.action`(9) / `shell.overlay#nv-console`(25) / `#novel-workspace-dialog`(20) / `#novel-split`(25) / `#novel-bind-dialog`(40) |

**三条容易踩的坑（都是它踩过的）**：

1. **工具行必须独立声明、且 `inject` 只能写硬依赖。** `lib/tools.js` 的 `inject=['tools']` 只声明 `tools`；novel-writing 服务走 `ctx.get()` 探测。注释里明写原因：**"不得加入 inject，加入会使未装 bundle 的预设无法挂载。"**
2. **`apply()` 应当返回清理函数。** 它的客户端 `apply` 返回一个函数，负责复位控制台、关分栏、移除事件监听、退订服务、移除注入的 `<style>`。**不返回清理函数 = 卸载后留一地垃圾。**
3. **HTTP 路由要自带安全三件套**：`enabled=false → 503`；非回环且未开 `apiPublic → 403`（回环判定以 `socket.remoteAddress` 为准，Host 头仅兜底）；POST 走同源校验（Origin/Referer 须匹配 Host + content-type 含 `application/json`）防 CSRF；body 上限 4 MB。

**一条最值得学的边界纪律**：**门禁下沉到服务层。** `saveChapter` 先跑 gateCheck，不通过且非 `force` 就 throw；`recordReview` 强制 findings ≥ 2 且 **pass ⇔ score===100 且 hardGates 为空**；`publish` 第一件事校验 `guardrails.release_allowed===true`。注释明确"与 HTTP 工作台同一收口"——**规则写在服务层，工具和 UI 都绕不过去**。这是"门禁从靠 AI 自觉升级为代码强制"的真正含义。

## 4. 边界层模式（Boundary Layer）：本报告认为最值得抄的一手

【实测】`dsh-novel-writing\lib\host-boundary.js`（17 KB）是这个插件工程上最聪明的设计。它把**所有**对宿主的调用收口到一个文件：

```js
// host-boundary.js 导出的收口函数（实测 L24-103）
export { z, Service }                                    // 宿主类型/基类
export const BOUNDARY_MAP = { ... }                      // 边界映射表
export const SERVICE_NAME = 'novel-writing'              // 服务名（单一事实源）
export const EVENT_CHANGED = 'novel-writing/changed'     // 事件名
export const hostInject = ['settings']                   // inject 声明源
export function registerSettings(ctx, ns, schema)        // 注册设置节
export function readSettings(ctx, ns)                    // 读设置
export function getWebServer(ctx)                        // 拿 webServer（可能 undefined）
export function registerRoute(webServer, route)          // 挂 HTTP 路由
export function onLifecycle(ctx, fn, label)              // 生命周期钩子
export function loggerOf(ctx) / logWarn(ctx, msg)        // 日志
export function emitChanged(ctx, payload)                // 发变更事件
export function presetRoot() / presetDir(id)             // $DSH_HOME/.agent-presets 路径
export function detectHostCapabilities(ctx)              // 宿主能力探测
export function contractProjection()                     // 契约投影
export function warnCompatReport(report, sink)           // 兼容告警
export function selfCheckHost(ctx, sink)                 // apply 期自检
```

而 `index.js` 的模块注释里明写了这条纪律（原话大意）：

> 本文件的**全部宿主调用**经 `./host-boundary.js` 收口（宿主包导入 / settings 注册读取 / webServer 路由挂载 / `$DSH_HOME` 预设路径 / Service 基类与服务名 / 日志·事件·生命周期 + apply 期兼容自检）——**本文件零直连宿主 API**（smoke 收口断言机检）。宿主升级时服务端适配**只改边界层**。

【实测 `index.js:1-32` 头部注释 + 我用 grep 验证过：`index.js` 里 `ctx.` 出现 **0 次**——它拿到 `ctx` 后立刻透传给边界层函数，自己从不直接访问。这一点非常硬核，是可验证的架构约束，不是口号。】

**为什么这值得抄**：

| 问题 | 无边界的后果 | 有边界的收益 |
|---|---|---|
| 宿主升级改 API | 全仓库 grep 替换，漏一处就线上崩 | **只改一个文件** |
| 双闭包/版本漂移 | 插件自己装一份宿主包，`instanceof` 失败 | 边界层是唯一 import 宿主的地方，好审计 |
| 兼容性无人知 | 用户报"白屏"，无法定位 | `selfCheckHost` 在 `apply` 期就打印结构化告警 |
| 契约漂移 | 宿主改字段名，插件静默失效 | `host-contract.mjs` + CI 双向对账会红 |

**具体可搬的动作**（无论写不写 DSH 插件）：

1. 建一个 `host-boundary` 模块，**把所有外部依赖的调用集中在这里**；
2. 给每个外部符号**起业务名**（`getWebServer` 而不是 `ctx.webServer`），以后宿主改名只改边界层；
3. `apply` 期跑一次**能力自检**，缺面就**降级 + 告警**，绝不阻断加载；
4. 用 **smoke 断言**机检"主文件零直连宿主"（他们就是这么做的）。

## 5. 宿主兼容契约（host-contract）：把"宿主耦合"变成可对账的数据

【实测】`lib/host-contract.mjs`（77 KB）是**纯数据**文件（零宿主 import、零运行时逻辑）。它登记这个插件用到的**全部宿主耦合点**，分类成六个「面」（face）：

| 面 | 内容 |
|---|---|
| 1 | 宿主导入面（用了哪些宿主导出符号） |
| 2 | 客户端 API 面（`remote.<ns>` 服务） |
| 3 | DOM/前端约定面（**CSS 类名正则、槽位名、selector 字面量**） |
| 4 | 安装注册面（`package.json` 的 dependencies/bundles 字段） |
| 5 | 预设 manifest 面（preset 行的键集） |
| 6 | 版本环境面 |

每条 item 记录：`id` / `kind` / `face` / `necessity`（必须 or 可选）/ `symbol` / `golden`（期望值）/ `line`+`note`（源码位置）。

**它解决了什么具体问题**（这是我看过最好的例子）：【实测 `docs/review/COMPAT-002-R1.md`、`COMPAT-005-R1.md`、`UX-060-R1.md`】

- **"纯数据契约"本身也要被守卫**：他们发现 JSON 往返检查对**函数值天然免疫**（method 简写、getter 会被 `JSON.stringify` 丢弃后往返仍相等 → 假通过）。于是加了递归 own-property 检查（每个自有属性必须是数据属性，值类型白名单 `string/number/boolean/null/array/plain-object`），并把"守卫能拦什么、不能拦什么"**写进契约注释**——避免消费者高估保证。
- **登记遗漏会造成三面零信号**：他们记录了一个实例——`lib/client.js` 里一个侧栏类名正则长期未登记，导致宿主改类名时 **CI、smoke、诊断三处全都不报**。于是定了条纪律（P-10）：**新增/修改任何宿主耦合字面量必须同步登记契约 + 补双向 ⊆ 对账断言，漏登记 = 三面零信号**。
- **版本探测轨**：CI 每天跑一次 `npm view @deepseek-ai/dsh versions --json`，与契约覆盖的版本对账，上游发新版就红——且明确**只读元数据、不 install、不执行宿主代码**（供应链安全）。
- **诚实披露探测窗口**：他们明写"探测是每日一次、且只在 CI 侧，**窗口期内宿主升级仍可能先于探测到达用户**；探测不是实时防护"。兜底是**加载期防线**（`[nv-compat]` 结构化告警 + 客户端按域降级 + 设置页诊断区），并总结成一句：「**有探测 ≠ 无窗口**」。

**可搬用的最小版本**（一个人写插件也做得到）：

```
host-contract.mjs   ← 纯数据，登记所有宿主耦合符号 + 期望值 + 源码位置
scripts/probe.mjs    ← 只读探测，与契约 diff，输出缺面报告
test/smoke.mjs       ← 断言「登记项」与「实际用到的」双向 ⊆
CI 每日 job          ← npm view 对比上游版本
```

## 6. 客户端注入与 UI 挂载

【实测】`package.json` 的 `dsh` 字段是插件的元数据入口：

```jsonc
"dsh": {
  "bundle": { "patch": "./cordis.patch.yml" },   // 宿主侧：composition 补丁
  "client": {                                     // 浏览器侧：客户端 bundle
    "platform": "web",
    "inject": [                                   // 必须在场的宿主客户端包
      "@deepseek-ai/dsh-client-ui-settings",
      "@deepseek-ai/dsh-client-locale",
      "@deepseek-ai/dsh-api-remotes"
    ]
  }
}
```

**关键机制（也是我们撞墙的原因）**：

- **`client.inject` 是硬约束**。三个插件的 `inject` 面各不相同：
  - `dsh-novel-writing` 要 `dsh-client-ui-settings` / `dsh-client-locale` / `dsh-api-remotes`
  - `dsh-novel` 要 `dsh-client-runtime` / `dsh-client-ui-conversation`
  - `oh-story-dsh@0.1.9` 要 `dsh-client-store` / `dsh-client-ui-conversation` / `dsh-client-ui-layout` / `dsh-client-ui-tool`
  本机（0.1.5-rc.1）**没有** `dsh-client-store`、`dsh-client-ui-slots`、`dsh-client-runtime`——这就是上次结论"装不了"的**根因**：不是配置错，是**客户端注入面在那一代还不存在**。
- **UI 挂载用槽位 + overlay**。【实测 `dsh-novel-writing\CHANGELOG.md`】它用 `shell.overlay`（全屏覆盖层，带 `id`/`order`/`zIndex`）做"管理控制台"和"创作工作台分栏"，用 sidebar 区块做入口。会话切换用 `sessions.open`，预设切换用 `agentPresets.select`，并把 UI 状态（宽度/换边/排序）存 `localStorage`。
- **实时渲染靠"版本号 + 事件"**。【实测 `index.js` 头部注释】每次写入递增 `version` 并 emit `novel-writing/changed`；浏览器侧 **2 秒轮询** overview 对比版本再重渲染。这是"插件没有推送通道时怎么做实时"的实用解法。
- **几何跟随宿主布局**是一种脏活但必须做：控制台的定位要取会话根的 `bounding rect`，用 `ResizeObserver` + `MutationObserver(data-phase)` 跟随重定位，并在"无会话根"时降级到侧栏右缘。**结论：想跟宿主 UI 拼装，就要接受跟宿主 DOM 耦合，而耦合点必须登记契约。**

# 第三篇｜网文商业流程与量化阈值

## 6.5 最完整的阶段流水线：19 个阶段 + 四级门禁

【实测，详见 `dsh-novel-writing-analysis.md` §B1】`dsh-novel-writing` 的 `using-writing-workflow` SKILL 定义了目前我见到的**最完整的商业写作流水线**，值得作为总流程骨架：

```
① 作品类型选择 → ② 平台调研 → ③ 竞品分析 → ④ 题材选择 → ⑤ 作品确认
→ ⑥ 创作规划 → ⑦ 大纲撰写 → ⑧ 大纲审查 → ⑨ 章节细纲 → ⑩ 细纲审查
→ ⑪ 正文生成 → ⑫ AI 合规评估 → ⑬ 质量审查
→ ⑭ 上架策略 → ⑮ 变现策略 → ⑯ 开篇优化 / 文风学习（可选）
→ ⑰ 数据监控 → ⑱ 读者互动
```

**四级门禁（逐级、任一失败即停）**：

| 门禁 | 校验内容 |
|---|---|
| **F1 文件存在** | 上一阶段的产出文件是否真的落盘 |
| **F2 状态更新** | `workflow-state.json` 的 stage 是否更新 |
| **F3 内容标准** | 产出文件是否满足该阶段的最低内容要求 |
| **F4 质量门禁** | 仅关键阶段启用；**失败不提供"跳过"选项** |

**关键设计**：门禁的检查方式是**"读输出文件直接验证"，而不是读审查报告**——防止"报告说通过了但文件不达标"。并且**关键阶段（大纲审查 17 子项、细纲审查 11 子项、质量审查 15 硬门禁）都要求总分 = 100。**

**状态文件结构**（`novel-project/workflow-state.json`）里有一个字段设计特别值得抄：

```jsonc
"guardrails": {
  "continuity_mode": "...",
  "latest_passed_chapter": N,
  "latest_ai_path": "A",          // AI 参与度路径，见 §9
  "release_allowed": true,         // 能否上架
  "monetization_allowed": true,    // 能否变现
  "latest_drift_score": ...
}
```

**把"能不能上架/变现"做成布尔标志位**，让下游阶段（上架策略、变现策略）在入口硬校验——这是把合规与质量从"建议"变成"闸门"的正解。

## 9. 数据闭环的四级调整（防"数据一掉就乱改"）

【实测 `README.md:22` + `data-driven-optimization\SKILL.md`】信号触发后，调整分四级**且必须用户确认**：

```
章内（改字句/补钩子）→ 细纲（重排情节点）→ 大纲（调卷结构）→ 题材（换赛道/止损）
```

**这四级顺序本身就是纪律**：优先在最小作用域解决问题，**不许因为追读掉了就直接改题材**。

另外一条我觉得最狠的设计：**A/B/C 三级 AI 参与度分流**——按 AI 参与程度分级，并**把结论直接落成两个硬标志位 `release_allowed` / `monetization_allowed`**。【实测 `dsh-novel-writing-analysis.md` §B5】

| 级别 | 口径 | 标志位 | 后果 |
|---|---|---|---|
| **A 平台安全** | AI 仅做资料查询 / 市场调研 / 校对语法 / 起名灵感 / 要素级灵感 / 粗纲辅助；**不允许 AI 生成正文段落、续写情节、生成核心对话** | `release_allowed=true`、`monetization_allowed=true` | 可上架可变现 |
| **B 灰区** | AI 生成场景素材 / 对话初稿 / 辅助改写部分段落；人类完成核心剧情·情感·个性化表达，且素材经大幅人工改写 | **两个 flag 均 false** | 仅建议练习 / 自发平台 / 非签约；想签约须大幅改稿重评 |
| **C 高风险** | AI 生成完整章节初稿 / 连续多章 AI 主导 / 证据链不完整 | **直接阻断** | 阻断上架与变现，并列财务风险（签约被拒、作品下架、永久取消签约资格） |

**判据的定义很精确**（值得记）：**"不是像不像 AI，而是 AI 是不是在替代人类做创作主体。"**

**落地刚性**：结论必须**回写**到状态文件的 `guardrails.latest_ai_path / release_allowed / monetization_allowed`；原文一句纪律——**"只生成日志但不回写状态，视为流程未完成"**。且 `publish` 与 `monetization` 两个入口各自校验对应 flag（服务层强制，工具与工作台同一收口）。

**配套的"人味注入清单"**（每章至少 5 项）：独特比喻 / 不规则句式 ≥3 处 / 非视觉感官细节 ≥2 处 / 口语化对话 / 个人化描写 / 情绪留白 / 节奏变化 / 场景脏细节。并逐章生成"创作证据链留存包"（`novel-project/13-creation-logs/chapter-XXX-log.md`），记录 AI 对话过程与首稿留存，让作者被平台质疑时有东西自证。

这是**平台 2026 年严打 AI 水文**背景下的合规应对，属"想赚钱就必须处理"的现实问题——**注意：这一条与我们用 AI 辅助写作直接相关，值得单独正视。**

## 10. 三套"硬门禁"体系对比

三个插件都做了门禁，但粒度不同：

| | 门禁形态 | 规模 | 特点 |
|---|---|---|---|
| `dsh-novel-writing` | **15 项硬门禁 + 9 维 100 分制**，**总分必须 = 100 才通过（99 分 = 不通过）** | 15 项 | 最严。任一门禁失败即阻断；零容忍 |
| `dsh-novel` | **判定五档**：`accepted` / `continue_with_warning` / `local_patch` / `rewrite_needed` / `stop_for_replan` | 5 档 + 10 审查维度 | 最可操作，**给的是"怎么改"而不是"过不过"** |
| `oh-story-dsh` | **确定性脚本 + 7 Gate**（去 AI 味）+ **S1—S4 严重度** | 脚本级 | 最工程化，含"缺细纲不许写正文"的**阻断型 hook** |

### 10.1 `dsh-novel-writing` 的 9 维评分制（详细）

【实测，详见 `dsh-novel-writing-analysis.md` §B2】100 分被**切成 6 份分给 6 个独立审查 Agent**，且**审查者与写作者绝对分离**：

| 维度 | 分值 | 归属审查员 | 判据要点 |
|---|---|---|---|
| 设定逻辑性 | 10 | continuity-reviewer（25 分） | 世界规则自洽、力量体系一致、**无"临时追加规则"**、无废设定 |
| 人物一致性 | 15 | character-world-reviewer（25 分） | 行为 / 对话 / 身份 / 关系 / 成长弧 |
| 情节逻辑性 | 15 | plot-logic-reviewer（15 分） | 因果链完整、伏笔"埋→推→收"、冲突不无故降级、**被动主角超 3 章扣分** |
| 时间线 + 数值 | 10 | continuity-reviewer | 时间连续、年龄同步、战力/经济数值稳定、时间跨度合理 |
| 结构质量 | 15 | plot-logic + commercial | 覆盖率 100%、偏离度 0%、信息释放节奏、**章末钩子是否兑现细纲承诺** |
| 文学质量 | 8 | engagement-reviewer（18 分） | 无连续 3 句同构、**感官描写 > 60%**、**口语化对话 > 80%**、视角一致、文风稳定 |
| 情感体验 | 10 | engagement-reviewer | 情绪曲线起伏、期待感、代入感、**爽点"铺垫→引爆→余韵"完整**、情感签名履约 |
| 平台商业化 | 10 | commercial-editor（10 分） | 平台核心指标达标 + 付费卡点 + **社交传播潜力**（是否有读者会截屏分享的段落） |
| AI 痕迹 + 原创性 | 7 | ai-compliance-officer（7 分） | 密度 ≤5% 优 / 5—15% 合格 / 15—30% 需优化 / >30% 不合格 |

**两条必须点出的设计**：

1. **"99 分 = 不通过"，且明文禁止协调者说"差一点没关系"。** 这是把"审查只有满分"做成硬约束，而不是态度。
2. **审查必须用独立 subagent**；主会话自检与独立审查**差 > 15 分时以较低分计**，并标注"审查一致性差异"。这条极聪明——它防的是"自己审自己总是给高分"。

### 10.2 付费部分的额外门禁（很少见，但很实在）

- **付费章开头 300 字内必须有即时回报**（禁过渡或回顾开头）。
- **付费后 3 章的爽点密度 ≥ 免费部分的 1.5 倍**。
- 付费章须标注：钩子类型（悬念 / 高潮前 / 反转 / 升级卡点）+ 预期转化强度 + **退款风险因素**。
- **回报分级配额**：小回报每 2—3 章 ≥ 1 次；**中回报间隔 ≤ 10 章**；大回报每卷末 1 次。
- **传播机制**：高唤醒情绪（敬畏 / 惊喜 / 愤怒）驱动分享，低唤醒（悲伤 / 满足）抑制分享；该插件引述"超级粉丝占 2% 读者，驱动 18% 消费、9 倍分享率"。

### 10.3 数据阈值是写在宿主代码里的（不是 prompt 里）

【实测 `dsh-novel-writing-analysis.md` §B4 / `lib/index.js` L1179-1223】它把信号阈值表**硬编码进宿主侧 `computeSignals()`**，注释自述"阈值来自源工作流数据监控 skill，硬编码为参考值"。这份实现比我上一轮建议的"排障手册"更硬：

| 信号 | 触发条件 | 级别 | 建议行动 |
|---|---|---|---|
| 完读率低 | 10 万字节点 < 10% | high | 触发开篇优化：重审前 3 章 |
| 章节流失 | 某章读完率 < 30% | high | 定位流失章 → 章节诊断与重写建议 |
| 追读下降 | 连续 3 天降 > 10% | high | 最近 3 章节奏/爽点分析 |
| 追读异动 | 单日降 > 10% | medium | 观察 |
| 收藏停滞 | 连续 7 天日增 < 10 | medium | 书名/简介/封面优化 |
| 口碑问题 | 同问题差评 ≥ 3 条 | medium | 提关键词 → 修改方案 → 回归验证 |
| 收益下滑 | 连续 4 周降 > 20% | high | 止损决策框架：停更 / 改向 / 完结 |

**闭环纪律**（原文一句话最准）：**"数据闭环的核心是'发现→定位→修复→验证'，不能只做前两步。"** 修复后必须走 **7 天观察期**再评估。

**调整级别**（防"一掉数据就大改"）：章内 → 细纲 → 大纲（走 REV 修订流程，**每卷 ≤ 2 次**）→ 题材/立意级（**仅数据连续 2 周恶化且用户主动提出，不允许 AI 单方触发**）。任何对策须以"方案 → 影响分析 → 预期收益/风险"三元组经作者确认。

**我推荐 `dsh-novel` 的五档判定**给个人作者用，理由：它把"不通过"细分成"局部改片段 / 重写关键段 / 停下来重规划"，直接对应动作。原文的常见情形→判定对照表也很实用：

| 情形 | 判定 |
|---|---|
| 零净变化；假钩；开篇劝退且全章空转 | `rewrite_needed` |
| 非标准引号对白外壳；括号夹注对白/内心；局部注水；单段口吻均质 | `local_patch` |
| 设定变更漏报（新人物/物品/关系等） | `local_patch` 或 `rewrite_needed` |
| 字数略越界 | `local_patch` |
| 字数严重偏离 | `rewrite_needed` |
| 与邻章/卷规划结构性冲突 | `stop_for_replan` |

# 第四篇｜结构化写作方法论

## 11. 「读者验收五问」：最省的章节自检

【实测 `dsh-novel\seed\skills\review\chapter\章节审查.md:9-17`】这是我在三个仓库里见到的**性价比最高的一段**——五句话，任何一项明确失败就不得判通过：

1. **开篇会不会让我想划走？**
2. **读完我能一句话说清"得到了什么"吗？**
3. **有没有哪段像说明书 / 复读 / 注水？**
4. **对白是否像不同的人在说话？**
5. **章末我是否想立刻看下一章（真期待，非假钩）？**

配套的"净变化"概念很好用：**写不出"一句话净变化" = 回报失败**。而且它的审查维度里有一条直接对准了我上一轮报告里的头号缺陷：

> **主角主动性**：主角是否用选择推动局面，而非纯旁观。

还有一条我记得很清楚的反例判据：**"被动主角超过 3 章 = 扣分"**（`quality-review\SKILL.md:108`）。这正好补上《混沌冠冕》那份分析里"主角无内在代价"的可操作替代指标。

## 12. 结构化实体模型（`dsh-novel` 的贡献）

【实测 `dsh-novel\seed\skills\` + `src\novel\schema.ts`、`domains.ts`、`template-fields.ts`，明细见 `dsh-novel-网文方法论笔记.md`】它把一部网文建模成 **1 个概述 + 13 个实体域**，每个实体有"谁写、谁审、什么字段"：

| 实体域 | 关键字段 | 防止的问题 |
|---|---|---|
| `overview`（概述） | `novels.blueprint_json`：一句话主轴 / 卖点 / 情感签名 | 目标不清 |
| `outline`（卷/章节点） | `ordinal` / `name` / `parentId` / `theme` / `conflict` / `majorEvents` / `content`（走向 + **章末期待**） | 章纲空转 |
| `role` / `roleRelation` | 人物硬设定、关系变化需有铺垫 | 人物前后不一 |
| `roleTimeline` | 人物状态随章变化 | 状态漂移 |
| `timeline`（事件轴） | `eventType`（含 `foreshadow`/`conflict`/`suspense`）/ `timeLabel` / `timePoint` / **`isResolved`** / **`resolveChapterNo`** | **伏笔丢失** |
| `world` | 世界规则（只保留**约束行动**的部分） | 设定百科 |
| `worldTimeline` | 世界状态变化 | 世界不随剧情走 |
| `level` | `abilities` / `promotionCondition`（每级须有新玩法或新限制） | 升级只加数值 |
| `item` / `itemTimeline` | 归属、流转、状态 | 道具凭空出现 |
| `creature` / `creatureTimeline` | 生物档案与出场 | 生物乱入 |
| `chapter`（章节点） | 见 §12.1 章节点合同 | — |

### 12.0 一条最值得记的建模习惯：「宿主域 + 履历域 + 状态位」

【实测，`dsh-novel-网文方法论笔记.md` §6】这套 schema 有个贯穿性的三元组设计，我认为是它最可迁移的一手：

```
宿主域（当前状态）   role / item / world / creature / level
    ↕ 一一对应
履历域（变化历史）   roleTimeline / itemTimeline / worldTimeline / creatureTimeline
    ↕ 配合
状态位（是否结清）   timeline.isResolved / resolveChapterNo
```

**为什么这三件要分开**：`role` 只存"现在是什么样"，`roleTimeline` 存"什么时候变成这样"，`timeline.isResolved` 管"这件事结清了没有"。三者分离后：

- **设定漂移** = 宿主域被改了但履历域没记（可检测）；
- **伏笔丢失** = `isResolved=false` 且 `resolveChapterNo` 早已过期（可检测，见 §12.2）；
- **人物前后不一** = 履历域里找不到当前状态的来源章（可检测）。

**可迁移结论**：**任何"会随剧情变化的东西"都要拆成"当前值 + 变更历史 + 结清标志"三份。** 这一个习惯能同时治住设定漂移、伏笔丢失、人物崩坏三类病。

### 12.1 章节点合同（把"可写性"做成字段级验收）

【实测 `outline\结构与卷章模板.md`】章节点必填字段与质量条：

| 字段 | 质量条 |
|---|---|
| `ordinal` + `name` + `parentId` | 界面显示"第 1 章 ××"，**不要把"第 1 章"写进 `name`** |
| `extra.conflict` | 阻力来自谁/什么，**禁止空话** |
| `extra.majorEvents` | **有序、可执行、因果相连**的必须事件；**禁止"了解设定 / 日常过渡"充数** |
| `content` | 走向 + **章末期待**（翻页欲合同，供正文对齐） |
| `extra.theme` | 本章主题，与冲突/事件一致 |

**两条硬纪律**：

1. **"章与章之间 `majorEvents` 应能看出因果（上章后果 → 本章前提），禁止可任意调换顺序的平行清单。"** —— 这是我认为最锋利的一条判据：**如果你能把两章的 `majorEvents` 互换而读起来都通顺，说明它们之间没有因果。**
2. **一卷一条大故事线，一章一条说明，禁止用"1—30 章"合并节点。**

**验收问法**（它写进 skill 里的自检）："随便看本章说明，**能否想象写成有冲突、有净变化、有章末期待的正文**？"

### 12.2 伏笔账本（治《混沌冠冕》的真实病症）

【实测 `world\伏笔账本.md`】生命周期明确为 **埋设 → 推进 → 提示 → 回收 → 后果**，落库映射到 `timeline` 的 `eventType=foreshadow` + `isResolved` + `resolveChapterNo`，并明确要求**不要只维护一张平行 Markdown 表当唯一真相**。

**三条禁忌（我认为是整套方法论里最准的一段）**：

- 大量埋伏笔从不回收；
- **回收只解释设定、不改变后续行动**；
- 用新万能设定覆盖未回收旧伏笔。

**这三条恰好就是《混沌冠冕》后半段的真实病症**——蛇神的蛋、贝黑莱特来源、摩根爱人辛西娅、拉杜格/深地-杜菈，全是"埋了没回收"；而"回收只解释设定"正是它大量伏笔的落地方式（解释了，但没改变任何后续行动）。

**回收质量的判据**（可直接用）：**"回收必须影响关系、规则或主线，不能回收完消失。"**

## 13. 黄金三章的两种表述（互相印证）

**表述 A（`dsh-novel`，按"义务"写）**【实测 `outline\黄金三章与验收.md:11-17`】：

| 章 | 必须交付 | 读者感到 |

**表述 B（`dsh-novel-writing`，按"要素"写）：Contract-Clock-Crucible**【实测 `opening-optimization\SKILL.md:33-40`、`creation-planning\SKILL.md:391-393`】：

## 14. 去 AI 味的硬规则（`oh-story-dsh` 的贡献）
【实测 `banned-words.md`、`deslop-gates.md`、`anti-ai-writing.md`、`long-format.md`】这套规则比我上轮报告里的"语言纪律"更硬，且**有反投机边界**：

**标点硬约束**：
- 正文（含叙述与对话）**禁用破折号 `——`/`—`、双连字符 `--`、省略号停顿**；停顿改用**句号、逗号、短句或动作断句**。
- **禁止通篇句号化**（语气被压平），也**禁止随机标点堆砌**（问号/感叹号不承载情绪功能）。原则：**质问才用问号，爆发峰值才少量感叹。**
- 例外白名单机制：本书明确允许时，登记在书级 `.deslop-whitelist`，且**必须登记完整获准原句**，不能登记"不是/没有"这种泛词来关掉整类检查。

**改稿的反投机边界**（这段写得非常清醒）：
> 不要为了"反检测"强制每句换行、把 `……` 改成 `........`、把 `地/得` 全改成 `的`、禁用所有顿号/"很"/"像"、强行开篇对话或按三番四证重排章节。**去 AI 味是润色，不是结构重写。**

**"删过头"的自我检查**：若整段只剩最短句、结构虚词被扫光、每个动作都带"了一下"式尾巴，就是**电报体**——要把非峰值叙述句恢复成自然白话。**"删的是废话，不是中文的自然冗余。"**

**禁用词密度分级**（可直接当仪表盘）：≤5 处/千字 = 轻度；6—15 = 中度；>15 = 重度。

**字数口径**：长篇用 `visible_chars_v1` 同口径测量，**内部带 ±12%，用户带 ±15%**；`under` 不补写（不自动加戏），`over` 最多做**一次**"净删且不增语义"的压缩。这条纪律很关键：**不靠增删凑字数**。

## 14.5 一个必须记住的教训：不要被"仓库里有的东西"骗了

【实测，我亲自复核过三处代码】`dsh-novel` 的 `seed/skills/genres/` 下有 **8 个题材的完整规则**（仙侠/历史/悬疑/末世/玄幻/科幻/言情/都市，每题材含 `overview/题材规则.md` + `review/outline/大纲审查.md`），看起来是这套方法论的重要资产。**但它们全是死代码——运行时根本不加载。**

三处独立证据（我逐处核对过原文）：

| 位置 | 原文 | 含义 |
|---|---|---|
| `src\novel\seed.ts:139` | `/** Seed generic skill markdown (genre-specific files under seed/skills/genres are not loaded). */` | 注释直接说明不加载 |
| `src\novel\seed.ts:83-93` | `DIR_TO_SECTION` = `overview / role / creature / level / world / timeline / outline / chapter / item` | **只有 9 个键，没有 `genres`** |
| `src\novel\schema.ts:91-93` | `DELETE FROM novel_skills WHERE folder = '题材' OR folder LIKE '题材/%'` | 启动时**主动删除**题材技能行 |
| `src\novel\store.ts:318-321` | `WHERE folder <> '题材' AND folder NOT LIKE '题材/%'` | 查询时**再过滤一次** |

**但同一仓库里的 `writing-style` 是活的**——它走**另一条独立加载路径**（`seed.ts:32-59` 单独读 `writing-style/<slug>/STYLE.md` 写入 `writing_styles` 表），含 3 个文风包：

| 文风包 | 出处 | 定位 |
|---|---|---|
| 大奉打更人风 | 卖报小郎君《大奉打更人》 | 第三人称紧贴主角的白话网文风：现代吐槽内心戏、探案推进、爽点刀光与社死幽默并存 |
| 黑道邪皇风 | 小白鼠《黑道邪皇》 | 冷硬都市黑道风：规矩立威、短句压迫、拟声落地，暴力写结果与气势，狠话少废话 |
| 黑道·大奉融合风 | 两者融合 | 以冷硬叙事为主、轻度借短句卸压节奏；专供丧尸末世下黑道规矩立威 |

**这条教训对写作工具有直接价值**：

1. **判定一个"方法论资产"是否有效，不看它写得多好，看它是否被加载。** 同样适用于你自己的素材库——**写下来但从不调用的模板等于没有**。
2. **题材规则不是不能读，但要明确它是"参考素材"而非"运行标准"。** 我读那 8 份题材规则是有收获的（例如玄幻的"四层压力：同辈 → 家族/宗门 → 地图势力 → 天道"、换地图"带走旧伏笔/旧敌/旧情感至少一项"），但**它是作者写了没启用的草稿，不是经验证的结论**——可信度要相应下调。
3. **文风包的加载方式是可用设计**：把"文风"做成独立的、可切换的资产表（而不是塞进题材），让同一套骨架套不同笔调。**这正是"换皮不换骨"的一种实现**。

## 16. 一页速查：可直接抄进流程的判据卡

```
【开篇契约 CCC】前300字=类型承诺(Contract) | 前10%=时间压力(Clock) | 前3章=不可退出处境(Crucible)
               （番茄口径：前200字无钩子=80%划走；前50页流失44%）

【读者验收五问】①开篇想不想划走 ②读完能否一句话说清"得到了什么"
                ③有没有像说明书/复读/注水 ④对白是否像不同的人在说话 ⑤章末想不想立刻看下一章

【硬门禁 · 数字版】
  连续3章弱钩子 → 阻断        第4-10章：≥6/7章强钩子，字数偏差±20%内
  连续5章情感签名偏离 → 阻断    连续10章无中回报 → 阻断
  40%-60%进度主角持续被动且无新变量 → 阻断
  字数偏差：±20%警告，±30%阻断   AI痕迹：≤15%合格，>30%不合格
  场景覆盖率须=100%  偏离度须=0%

【平台口味】
  番茄：前300字冲突 | 每800字一个微型悬念 | 章长2000-2500 | 指标=完读率+吸量
  七猫：前500字"冲突+人设+悬念"闭环 | 每1000字一小高潮（每8页插广告）| 情绪拉扯(播种→压抑→炸裂)
  起点：VIP章开头即给回报 | 章内要有停留20秒+的沉浸点 | 对话:描写=6:4 | 周二PK日质量最高
  晋江：情感细腻有层次 | 人设>情节 | 章末留讨论话题 | 文笔要求最高

【指标阈值】7日追读率>25%安全 | 10万字完读率>15%优/10-15%及格/<10%危险 | 20万字>8%
            三日留存>10% | 章节读完率>50% | 点击率<5%需优化 | 七猫精品门槛完读率>30%

【诊断映射】
  点击率<5% → 换标题/封面/前三句，A/B测3版
  追读<25% → 查第3-5章信息断层
  第2-3章断崖 → 第2-3章没接住钩子且没升级
  第5-10章阴跌 → 设定写早了，改"碎着写"，前10章只服务一条主线
  单章暴跌10点+ → 剧情硬转/人设崩，回扫定位"黄金断崖点"
  完读率低 → 算「安全字数=总字数×完读率」，其内每3000字一小高潮、每1.5万字一大转折；
             删开篇世界观说明书；结尾用"后果预告"；"获得型"改"损失型"

【改稿纪律】章内小改(3-5天窗口,做增补不做重写) | 大改留到下一卷伏笔
            调整分四级：章内→细纲→大纲→题材（不许一掉数据就改题材）
            字数：内部±12%、用户±15%；under不补写，over最多净删压缩一次

【标点硬规则】禁 `——`/`—`/`--` 与省略号作停顿 → 用句号/逗号/短句/动作断句
             禁通篇句号化，也禁随机堆砌？/！  质问才问号，爆发峰值才少量感叹
             删过头=电报体（只剩最短句、动作都带"了一下"）→ 把非峰值句恢复白话
             去AI味是润色，不是结构重写

【伏笔账本】字段：埋设章 / 计划回收章 / isResolved / 回收后改变了什么
            生命周期：埋设→推进→提示→回收→后果；回收必须改变关系/规则/主线
            禁忌：大量埋从不回收 / 回收只解释设定 / 用新万能设定覆盖旧伏笔

【三段分离建模】宿主域(当前值) + 履历域(变更历史) + 状态位(是否结清)
                例：role + roleTimeline + timeline.isResolved/resolveChapterNo
                一个习惯同时治：设定漂移 / 伏笔丢失 / 人物崩坏

【章纲两条硬判据】① majorEvents 必须因果相连 —— 若两章的事件互换后读起来仍通顺，说明没有因果
                  ② 每章必须有"章末期待"字段（翻页欲合同）；写不出=该章空转
                  禁区：用"了解设定/日常过渡"充数；用范围节点覆盖多章

【判定五档】accepted | continue_with_warning | local_patch | rewrite_needed | stop_for_replan

【阶段门禁 F1-F4】文件存在 → 状态更新 → 内容标准 → 质量门禁（关键阶段无跳过选项）
                  检查方式是"读输出文件直接验证"，不是读审查报告
```

## 17. Agent 人设模板：一个可直接复用的写法

【实测 `agent-presets\novel-writing\agents\engagement-reviewer.md`】它的 16 个角色 Agent 都遵循同一个模板，我认为比"你是一个专业的小说审查员"这类空泛授权有效得多。模板有六段：

| 段 | 内容 | 作用 |
|---|---|---|
| **1 身份定位** | 给**名字**（"小鹿"）、**履历**（晋江 7 年责编 + 番茄 3 年运营）、**核心能力的一句话**（"你能用读者的身体阅读"） | 让模型有稳定的判断视角，而不是平均化的"专业口吻" |
| **2 座右铭** | 一句话立场（**"读者不付钱买正确，读者付钱买感受。"**） | 冲突时的裁决准则 |
| **3 擅长的事** | 3 条具体能力（精确标注"无聊开始处"／识别"正确但窒息"的段落／区分"不知不觉读完"和"怎么还没完"） | 把能力变成可执行动作 |
| **4 痛恨的事** | 3 条反模式（"这段很重要所以不能删"／技术正确但无感情／用信息密度替代阅读体验） | **反向约束，比正面要求更有效** |
| **5 职责范围（负责/不负责）** | 明确划边界：不负责连续性、不负责 OOC、不负责情节逻辑、不负责商业适配 | **防止 16 个 Agent 互相重叠、重复扣分** |
| **6 最低输出要求 + 防放水** | 逐项判定 + 至少 2 个带原文引用的发现 + 明确强度判定；**"如果你返回'本章体验良好，无问题'，将被驳回重新审查"** | 防"敷衍通过" |

**其中两条设计我认为最值得抄**：

**① "负责 / 不负责"的显式划界。** 16 个审查员如果不划界，就会出现"同一个问题被五个 Agent 各扣一次分"，作者改起来无所适从。它把 9 维评分**切开分给不同角色**：阅读体验官管文学质量与情感、连续性审查员管事实一致、人物世界观审查员管 OOC、情节逻辑审查员管因果、商业编辑管平台适配。

**② "防放水"条款。** 直接规定"给不出具体发现 = 审查被驳回"，并给了人设动机（这个角色"曾经拒绝过一部场景覆盖率 100%、偏离度 0%、Bible 完全合规的作品，理由是'它正确得令人窒息'"）。**这解决的是 AI 审查最常见的失效模式：什么都通过。**

**可迁移到个人写作流程**：即使不用多 Agent，也可以拿这套模板给自己写**一张"审稿人卡"**——固定一个视角（例如"连载读者 + 平台运营"）、一句裁决准则、3 条反模式、以及"必须给出 N 个带位置的具体发现，否则不算审完"。这比我原报告里的"每章五问"更抗敷衍。

## 18. 四条我认为最值得记住的判断

1. **"读者在 300 字内必须知道这是什么类型的故事"** —— Contract 这条比"前 300 字要出冲突"更本质。冲突可以有很多种，但**类型承诺错了，后面的冲突都白写**。
2. **"评论区是诊断室，不是需求池"** —— 加上分诊规则（3—5 条定位问题段；3 个独立读者同说一件事 = 结构问题；违反主线设定/替作者规划剧情的评论必须忽略），这套过滤法能省掉大量被读者带偏的时间。
3. **"有探测 ≠ 无窗口"** —— 这是工程上的诚实，也是写作上的诚实：**任何门禁、任何数据指标，都不能替代你本人把那章读完。** 该插件自己在 AI 痕迹评估里就写了免责："此评估由 AI 完成，有结构性盲点，不能替代平台审核。"
4. **"仓库里有 ≠ 运行时会用"** —— `dsh-novel` 的 8 份题材规则写得挺完整，但三处代码证明它运行时根本不加载（§14.5）。**判断一份方法论资产是否可信，先确认它是否被真正使用**；同理，你自己写了却从不调用的模板，等于没写。
